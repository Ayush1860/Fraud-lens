## What the profile showed

- **Before the fix, one worker used far more CPU than one thread can** (the service CPU column). A uvicorn worker runs Python on one thread, so the extra CPU could only be XGBoost's OpenMP threads, which it starts on every core even to score a single row and which keep spinning between requests. Postgres stayed at a small fraction of a CPU.
- **Adding workers made it worse.** Three workers, each with an OpenMP thread per core, oversubscribed the four CPUs shared with Postgres, Redis and Locust: the model and explanation stages slowed sharply (compare the stage tables in each report) and throughput fell below one worker's.
- **The fix:** score on one thread per process (`FRAUDLENS_MODEL_THREADS`, default 1). One row per request gains nothing from more. A single worker then stays near one CPU, and three workers scale instead of competing.
- **Where time goes now.** The database stage, an insert and commit per decision, is the largest stage at every rate; it grows under load mostly because requests queue for the event loop and the connection pool, not because Postgres is busy.
- **Degraded responses** at the highest rate are requests whose card lock was not free within 150 ms: the service scores them from the transaction alone rather than letting latency grow without bound.

## Caveats

- Each run landed on whatever runner GitHub assigned, and the CPU models differ between runs. Compare CPU shares and throughput ceilings across runs, not millisecond-level differences.
- The model is a synthetic one with the released model's size (398 trees, depth 6); timing depends on tree count and depth, not on what the trees learned.
- The load generator shares the machine with the service, so the highest rates measure the whole box, not the service alone.
